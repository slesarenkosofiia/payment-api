# Secure Payment API

## Практическое задание: Вариант 2

**Тема:** Защищённый API для проведения платежей с tokenization и SSO.

Данный проект реализует учебный микросервис `payment-api`, который принимает запросы на проведение платежей банковской картой и демонстрирует основные архитектурные механизмы безопасности:

- SSO / OAuth2 через JWT Access Token;
- проверку прав доступа через `scope=payment`;
- валидацию банковской карты алгоритмом Luhn;
- токенизацию PAN;
- отказ от хранения PAN и CVV;
- маскирование номера карты в логах;
- шифрование чувствительного токена;
- unit-тест, проверяющий, что полный номер карты не попадает в логи;
- архитектурное описание TLS/mTLS и соответствия PCI DSS.

---

# 1. Цель проекта

Цель проекта — показать, как должен быть устроен безопасный API для обработки платежей.

В платёжных системах нельзя просто принять номер карты и сохранить его в базу данных или вывести в логи. Это нарушает требования безопасности, особенно требования PCI DSS.

Поэтому в проекте реализован следующий подход:

1. Клиент отправляет запрос на оплату.
2. API проверяет JWT-токен.
3. API проверяет, что у токена есть право `scope=payment`.
4. Номер карты проверяется алгоритмом Luhn.
5. Полный номер карты не логируется.
6. Вместо номера карты создаётся токен.
7. Токен шифруется.
8. В ответ возвращается статус операции и зашифрованный токен.

# 6. Реализация JWT / SSO

## 6.1. Зачем нужен JWT

Endpoint `/payments` не должен быть доступен всем подряд.

Поэтому перед обработкой платежа API проверяет JWT Access Token.

JWT содержит информацию о пользователе или сервисе, например:

```json
{
  "sub": "user-123",
  "scope": "payment",
  "iss": "corporate-idp",
  "aud": "payment-api"
}
```

Где:

| Поле | Значение |
|---|---|
| `sub` | Идентификатор пользователя |
| `scope` | Права доступа |
| `iss` | Кто выпустил токен |
| `aud` | Для какого сервиса предназначен токен |

---

## 6.2. Файл `app/auth.py`

Файл `auth.py` отвечает за создание и проверку JWT.

Пример логики проверки:

```python
if payload.get("scope") != "payment":
    raise HTTPException(status_code=403, detail="Not enough permissions")
```

Это значит:

- если токен есть;
- если он корректный;
- если в нём есть `scope=payment`;

тогда пользователь может вызвать `/payments`.

Если токена нет или он неверный, API возвращает ошибку.

---

## 6.3. Почему это SSO / OAuth2

В реальной системе пользователь проходит вход через корпоративный Identity Provider.

После входа Identity Provider выдаёт Access Token.

API не хранит логины и пароли пользователей. Он только проверяет токен.

Это соответствует идее SSO: аутентификация вынесена в отдельный доверенный сервис.

# 9. Проверка карты алгоритмом Luhn

Алгоритм Luhn используется для проверки номера банковской карты.

Он не проверяет, существует ли карта реально, но позволяет отсеять некорректные номера.

Пример тестового номера:

```text
4111111111111111
```

Этот номер часто используется как тестовый номер Visa.

Если карта не проходит Luhn-проверку, API возвращает:

```text
400 Bad Request
```

# 10. Маскирование PAN

PAN — это Primary Account Number, то есть полный номер банковской карты.

Полный PAN нельзя выводить в логи.

В проекте реализована функция:

```python
def mask_card(card_number: str) -> str:
    return "*" * (len(card_number) - 4) + card_number[-4:]
```

Пример:

```text
4111111111111111
```

превращается в:

```text
************1111
```

Это важно, потому что логи могут просматривать:

- разработчики;
- администраторы;
- системы мониторинга;
- службы поддержки.

Если полный номер карты попадёт в логи, это будет серьёзным нарушением безопасности.

---

# 11. Токенизация карты

Токенизация — это замена реального номера карты случайным токеном.

В проекте токен создаётся так:

```python
def tokenize_card(card_number: str) -> str:
    return "tok_" + uuid.uuid4().hex
```

Пример токена:

```text
tok_7e93075eed5647f0bcbd09ee34f33bdc
```

Смысл токенизации:

- реальный номер карты не хранится;
- для последующих операций можно использовать токен;
- при утечке токена злоумышленник не получает настоящий номер карты.

---

# 12. Отказ от хранения CVV

CVV относится к чувствительным аутентификационным данным.

В проекте CVV:

- принимается в запросе;
- не сохраняется;
- не логируется;
- не возвращается в ответе;
- не используется после обработки запроса.

Это соответствует принципам PCI DSS.

---

# 13. Шифрование данных в покое

После создания токена он шифруется.

Для этого используется библиотека `cryptography` и механизм Fernet.

Файл:

```text
app/crypto.py
```

Пример логики:

```python
fernet.encrypt(value.encode()).decode()
```

В ответе API возвращает:

```json
{
  "encrypted_card_token": "gAAAAABq..."
}
```

Это значит, что открытый токен не передаётся дальше в явном виде.

---

# 14. Ключ шифрования

В учебной версии, если переменная окружения не задана, ключ генерируется автоматически.

При запуске можно увидеть предупреждение:

```text
WARNING: demo Fernet key generated. For real use, store it in environment variable.
```

Это означает:

- для демонстрации ключ создаётся автоматически;
- для реальной системы так делать нельзя;
- в production ключ должен храниться вне кода.

Правильные варианты хранения ключей:

- переменная окружения;
- HashiCorp Vault;
- AWS KMS;
- Google Cloud KMS;
- Kubernetes Secrets.

# 19. Соответствие PCI DSS

Ниже перечислены меры, реализованные в проекте.

## 19.1. PAN не хранится

Полный номер карты используется только во время обработки запроса.

После проверки карты создаётся токен.

PAN не сохраняется:

- в базе данных;
- в файлах;
- в логах;
- в ответе API.

---

## 19.2. CVV не хранится

CVV не сохраняется и не логируется.

Это важно, потому что CVV запрещено хранить после авторизации платежа.

---

## 19.3. Используется токенизация

Реальный номер карты заменяется токеном.

Для повторных операций можно использовать токен, а не PAN.

---

## 19.4. Логи не содержат полный номер карты

В логах используется только маска:

```text
************1111
```

Это уменьшает риск утечки платёжных данных через лог-файлы.

---

## 19.5. Контроль доступа

Endpoint `/payments` доступен только при наличии JWT Access Token.

Также проверяется право:

```text
scope=payment
```

Это реализует разграничение доступа.

---

## 19.6. Шифрование чувствительных данных

Токен карты шифруется с помощью Fernet.

Это демонстрирует защиту чувствительных данных в покое.

# 20. TLS и mTLS

В учебной локальной версии приложение запускалось по адресу:

```text
http://127.0.0.1:8000
```

Но в промышленной архитектуре должны использоваться TLS и mTLS.

## 20.1. TLS

TLS нужен для защиты канала между клиентом и `payment-api`.

Без TLS злоумышленник в сети может перехватить:

- номер карты;
- CVV;
- JWT-токен;
- сумму платежа.

С TLS трафик шифруется.

---

## 20.2. mTLS

mTLS нужен между внутренними сервисами:

```text
payment-api → payment processor
```

При mTLS проверяется не только сервер, но и клиент.

Это значит:

- `payment-api` проверяет сертификат платёжного процессора;
- платёжный процессор проверяет сертификат `payment-api`.

Если клиентский сертификат отсутствует или неверный, запрос отклоняется.

---

## 20.3. Архитектурная схема TLS/mTLS

```text
Client
  |
  | HTTPS / TLS
  v
payment-api
  |
  | HTTPS / mTLS
  v
payment processor
```

---

# 21. Имитация атаки перехвата трафика

Если передавать данные без TLS, злоумышленник может увидеть содержимое HTTP-запроса.

Например:

```json
{
  "card_number": "4111111111111111",
  "cvv": "123",
  "amount": 1000
}
```

Поэтому в реальной архитектуре нужно использовать HTTPS.

TLS предотвращает чтение данных при перехвате трафика.

mTLS дополнительно предотвращает подключение недоверенных внутренних сервисов.

---

# 22. Non-repudiation транзакций

Non-repudiation означает невозможность отказаться от факта совершения операции.

В проекте для этого используется:

- уникальный `transaction_id`;
- JWT с идентификатором пользователя `sub`;
- логирование события обработки платежа;
- контроль доступа через `scope`.

В промышленной системе дополнительно нужно использовать:

- подписанные audit-логи;
- централизованное хранилище логов;
- временные метки;
- защиту логов от изменения;
- цифровую подпись критичных событий.

---

# 23. Ротация ключей шифрования

Для реальной системы ключи шифрования нужно периодически менять.

Рекомендуемый подход:

1. Использовать версии ключей:

```text
key_v1
key_v2
key_v3
```

2. Новые данные шифровать новым ключом.
3. Старые данные постепенно перешифровывать.
4. Хранить версию ключа рядом с зашифрованным значением.

Пример:

```json
{
  "encrypted_card_token": "...",
  "key_version": "v2"
}
```

Это позволит понять, каким ключом расшифровывать конкретную запись.

# 24. Ответы на контрольные вопросы

## 24.1. Почему выбран OAuth2/JWT?

Для API удобно использовать JWT Access Token, потому что токен передаётся в каждом запросе в заголовке:

```text
Authorization: Bearer <token>
```

API может проверить токен без хранения сессий на сервере.

Также JWT содержит claims, например:

- `sub`;
- `scope`;
- `iss`;
- `aud`.

В данном проекте используется claim `scope=payment`, чтобы разрешить доступ только к платёжному endpoint.

---

## 24.2. Как обеспечивается non-repudiation?

Каждая транзакция получает уникальный `transaction_id`.

JWT содержит идентификатор субъекта `sub`.

В реальной архитектуре дополнительно должны использоваться подписанные и неизменяемые audit-логи.

---

## 24.3. Какие угрозы покрывает шифрование в покое?

Шифрование в покое защищает от:

- чтения данных при утечке базы;
- чтения резервных копий;
- прямого доступа к файлам без ключа.

Но оно не защищает от:

- утечки ключа;
- вредоносного кода внутри приложения;
- администратора с доступом к памяти процесса.

---

## 24.4. Какие угрозы покрывает шифрование в движении?

TLS защищает от:

- перехвата трафика;
- чтения данных в сети;
- MITM-атак при корректной проверке сертификатов.

mTLS дополнительно защищает от подключения недоверенных сервисов.

---

## 24.5. Как выполняется ротация ключей?

Ротация выполняется через версионирование ключей.

Новые данные шифруются новым ключом.

Старые данные постепенно расшифровываются старым ключом и заново шифруются новым.

1. Запуск FastAPI-сервиса.
2. Получение JWT через `/demo-token`.
3. Авторизация в Swagger.
4. Успешный вызов `POST /payments`.
5. Ответ `200 OK`.
6. Возврат `status=approved`.
7. Возврат уникального `transaction_id`.
8. Возврат зашифрованного токена.
9. Запуск unit-теста.
10. Проверка того, что полный PAN отсутствует в логах.

# 26. Итоговый вывод

В результате был реализован защищённый API для обработки платежей.

Проект показывает основные принципы архитектурной безопасности:

- централизованная аутентификация через JWT;
- контроль доступа по scope;
- отказ от хранения PAN и CVV;
- токенизация банковской карты;
- маскирование чувствительных данных в логах;
- шифрование токена;
- проверка безопасности логов через unit-тест;
- архитектурное описание TLS/mTLS;
- соответствие основным принципам PCI DSS.

Таким образом, проект соответствует требованиям варианта 2 практического задания и может быть использован как демонстрационный пример безопасного платёжного API.
